# Evaluation

Claims of "AI-powered detection" are worthless without measurement. Every
metric referenced anywhere in this project (README included) must be
calculated from this test suite, run and re-runnable via `make evaluate` —
never asserted from memory or vibes.

## 1. Detection engine evaluation

Dataset: labeled synthetic event sequences in `scenarios/`, each with a
`ground_truth` describing which rule(s), if any, should fire.

Metrics:
- Precision, recall, F1 per rule and in aggregate
- False-positive rate

## 2. Anomaly detection (ML) evaluation

Dataset: the same scenario library, since Isolation Forest is unsupervised
at training time but our synthetic scenarios carry ground-truth anomaly
labels for evaluation purposes.

Metrics:
- Precision, recall
- PR-AUC (more informative than ROC-AUC under class imbalance, which anomaly
  detection always has)

## 3. Agent evaluation

**Dataset:** 25–50 investigation scenarios, each specifying:

```
incident, ground_truth, relevant_events, expected_detections,
expected_attack_techniques, expected_severity, expected_evidence
```

Example:

```
Scenario: Brute-force authentication attack
Expected: severity=high, technique=T1110, evidence=events[1..17],
          no unsupported claims,
          recommendation includes "investigate source IP / account activity"
```

**Metrics:**
- Evidence grounding rate — fraction of cited evidence IDs that actually
  exist in the tool results returned during that run
- Tool selection accuracy — did the agent call the tools a competent analyst
  would call
- Incident classification accuracy vs. `expected_severity` /
  `ground_truth`
- ATT&CK mapping accuracy vs. `expected_attack_techniques`
- Hallucination rate — claims not traceable to any evidence source
- Unsupported-claim rate
- Completion rate — runs that reach `COMPLETED` rather than `FAILED`

Outputs: `evaluation/results.json` (machine-readable, per-scenario) and
`evaluation/report.md` (human-readable summary), regenerated by
`make evaluate`. The dashboard can optionally surface the summary metrics —
never hand-picked favorable examples only.

## 4. Security testing (see `docs/security/threat-model.md` §4–5 for threat
rationale)

| Test | Expected result |
|---|---|
| Prompt injection via event field content | Treated strictly as data; no instruction-following |
| Unauthorized tool call | Rejected with structured error |
| Privilege escalation (viewer → admin action) | HTTP 403 |
| SQL injection via search/filter input | Safely parameterized/rejected |
| Invalid/malformed model output | Caught by schema validation, retried, then fails cleanly |
| Malicious/poisoned RAG document | Cannot override system instructions |
| Excessive tool loop | Execution halts at `MAX_AGENT_STEPS` / `MAX_TOOL_CALLS` |

## 5. System performance

Measured, not estimated:
- p50 / p95 API latency
- Ingestion throughput (events/sec)
- Model inference time (ML scoring)
- End-to-end time from ingestion to incident creation for a full scenario
  replay

## 6. What "done" looks like for this document

This file describes the methodology. As the project is implemented,
`evaluation/report.md` (generated, not hand-written) becomes the actual
record of results, and the README links to the latest generated report
rather than restating numbers here.
